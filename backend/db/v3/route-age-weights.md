# 경로 연령대별 시설 가중치

경로 계산용 분류는 `UNDER_14` / `AGE_14_PLUS` 두 종류다. 19세 기준 `user_type`(ADULT/MINOR), 기존 `facility_type_weight`와 별개이며, 실제 경로 계산에는 새 `route_facility_weight`를 사용한다.

## 초기값

| 시설 | 만 14세 미만 | 만 14세 이상 |
|---|---:|---:|
| CCTV | 0.20 | 0.15 |
| 가로등/보안등 | 0.20 | 0.10 |
| 경찰시설 | 0.30 | 0.15 |
| 비상벨 | 0.25 | 0.15 |
| 편의점 | 0.15 | 0.15 |
| 소방서 | 0.20 | 0.15 |

이는 실측 안전 확률이 아닌 조정 가능한 서비스 초기 설정이다. 14세 이상은 기존 시설 보너스 값을 유지하고, 14세 미만은 조명과 도움을 받을 수 있는 시설을 더 높게 평가한다. 비상벨은 서버 설정에 포함하지만 현재 앱에 원본 시설 데이터가 없어 점수에 등장하지 않는다.

앱에서 불러온 시설 데이터로 종류마다 가장 가까운 시설 한 곳의 보너스를 계산한다. CCTV/경찰시설/편의점/소방서는 150m, 가로등은 100m 안에서 `가중치 × (1 − 거리 / 반경)`을 더한다. 기존 계산에서 일반 시설 전체 중 가장 가까운 한 곳만 선택하던 부분은 종류별로 평가하도록 바꿨다. 그래서 가까운 편의점 때문에 경찰시설의 보너스가 빠지지 않는다.

원점수는 `0.85 − 기존 위험구역 감점 + 시설 보너스 합`이고, 이후 기존 방식대로 지도 그래프의 min/max로 정규화한다. 안전 경로 A*의 안전 가중치 0.55와 최단 경로의 0.0은 공통이다. 경로가 두 연령대에서 반드시 달라지는 것은 아니며 시설 배치와 거리 차이에 따라 달라진다. 비회원은 계정 연령을 추정하지 않고 기존 기본 시설 보너스로 계산한다.

## 가입·기존 계정

- 새 앱의 가입 화면은 생년월일을 받아 `POST /api/auth/signup`의 `birthDate`(YYYY-MM-DD)에 보낸다. 회원 유형은 기존 만 19세 기준으로 정하고 미성년 가입에는 보호자를 입력받는다.
- 이전 클라이언트의 가입 요청은 `birthDate`를 생략할 수 있다. 기존 계정과 동일하게 새 앱에서 경로 계산 전에 입력하도록 한다.
- `GET /api/users/me`는 본인의 `birthDate`를 포함한다.
- `PATCH /api/users/me/birth-date`에 `{"birthDate":"2014-11-13"}`을 보내 등록·수정한다. 1900-01-01 이전, 미래, 누락 날짜는 거절한다. 회원 유형을 이 요청으로 바꾸지는 않는다.
- 기존 계정이 새 앱에서 경로를 계산할 때 생년월일이 없으면 날짜 선택 창을 표시하고 저장 후 다시 계산한다. 내 정보 화면에서도 수정할 수 있다.
- 생년월일은 사용자가 입력한 정보다. 법정대리인 확인·동의 기능을 의미하지 않는다. 기존 보호자 등록/연결 기능도 그 동의 절차를 대신하지 않는다.

## 경로 계산·기록

인증이 필요한 `GET /api/routes/safety-profile`은 본인의 연령대와 DB 가중치를 반환한다.

```json
{
  "ageBand": "UNDER_14",
  "birthDateRequired": false,
  "facilityWeights": {
    "CCTV": 0.2,
    "STREET_LIGHT": 0.2,
    "POLICE": 0.3,
    "EMERGENCY_BELL": 0.25,
    "CONVENIENCE_STORE": 0.15,
    "FIRE_STATION": 0.2
  }
}
```

위 예시는 `ApiResponse.data` 내부다. 생년월일이 없으면 `ageBand:null`, `birthDateRequired:true`, `facilityWeights:{}`를 반환한다. 가중치가 누락되거나 잘못 설정되면 다른 연령대의 값으로 대체하지 않고 오류로 처리한다.

앱은 경로를 계산할 때마다 이 API를 조회한다. 연령대나 가중치가 바뀌면 캐시한 그래프도 다시 계산하므로 생일 경과와 DB 조정이 반영된다. 조회 실패 시 로그인 사용자의 연령대를 임의로 바꾸지 않는다.

안내 시작 요청 `POST /api/routes`에 계산 당시 `safetyAgeBand`를 보낸다. 서버는 현재 연령대와 일치하는지 먼저 확인한 후 `route.safety_age_band`에 기록한다. 생일 경과 등으로 달라졌다면 재계산을 요구하고 진행 중인 경로를 취소하지 않는다. 계산된 시설별 `appliedScore`는 기존처럼 `segment_facility`에 저장한다. 이전 앱은 새 필드를 생략할 수 있고 그 경로의 스냅샷은 NULL로 남긴다.

## DB 가중치 조정 예시

```sql
UPDATE route_facility_weight SET weight = 0.25
WHERE age_band = 'UNDER_14' AND facility_type = 'STREET_LIGHT';
```

새 DB는 `01_full_schema.sql` → `03_seed_base.sql`, 기존 DB는 `09_route_age_weights.sql`을 적용한다. 두 경로 모두 같은 초기값을 만든다. 마이그레이션과 seed 재실행은 이미 존재하는 가중치를 보존한다.

스키마 적용 후 `tests/route_age_weights.sql`로 두 분류·시설 코드·음수 및 비유한 가중치·생년월일·경로 스냅샷 제약을 검증할 수 있다. 이 스크립트의 테스트 데이터는 ROLLBACK된다.
