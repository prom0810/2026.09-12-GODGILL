# 공통 시설 지표와 경로 연령대

현재 기본 정책은 **COMMON_WITH_POLICE_V3**다. 경찰시설 접근성을 포함하며 두 연령대에 같은 시설 가중치를 적용한다. `UNDER_14` / `AGE_14_PLUS`는 서비스 분류로 유지하며 14세를 보행 위험의 과학적 경계로 간주하지 않는다. 검증된 입력이 마련되기 전까지 연령 보정은 0이다. 19세 기준 `user_type`(ADULT/MINOR), 기존 `facility_type_weight`와 구분하며 실제 설정은 `route_facility_weight`를 사용한다.

## 초기값

| 시설 | 만 14세 미만 | 만 14세 이상 |
|---|---:|---:|
| 방범 목적 CCTV | 0.02 | 0.02 |
| 가로등/보안등 | 0.04 | 0.04 |
| 경찰시설 | 0.04 | 0.04 |
| 비상벨 | 0 | 0 |
| 편의점 | 0 | 0 |
| 소방서 | 0 | 0 |
| 합계 | **0.10** | **0.10** |

이 값은 실험용 서비스 설정이며 연구에서 산출한 계수나 범죄 감소 확률이 아니다. 경찰시설 근접성은 도움을 요청할 수 있는 시설에 대한 접근성을 반영하는 서비스 요소로 포함한다. CCTV·조명과 예산을 나누어 총량을 0.10으로 제한했다. 소방서의 보행 위험 보정, 비상벨 작동, 점포 영업 여부는 미확인이라 나머지 값은 0이다. 앱과 서버 모두 합계 예산을 검증한다. 비회원도 같은 공통값을 사용한다.

CCTV는 원본 목적에 `방범`이 포함된 경우만 사용한다. 교통단속·목적 미상 카메라는 제외한다. 실제 촬영 방향·가림·운영 여부와 가로등의 실제 조도·작동 여부는 확인하지 못하므로 제한적인 근접성 대리 지표로 취급한다. 종류별 가장 가까운 유효 시설 한 곳을 사용하며 수량을 곱하지 않는다. 가중치 0인 시설은 기여 내역에 넣지 않는다.

경찰시설 조회는 시설 표시 필터와 별도로 수행한다. 지도에서 시설 마커를 숨겨도 조회한 경찰시설이 계산에서 제외되지 않는다. 경로 계산은 진행 중인 시설 조회를 기다린 뒤 최신 결과를 사용한다. API 키·조회 범위·원본 데이터에 따라 확보하지 못한 시설까지 있다고 추정하지는 않는다.

검색 반경은 CCTV·경찰시설 150m, 가로등 100m의 기존 거리 감쇠 휴리스틱이다. 실제 촬영·조명 범위나 도움 도달 시간으로 검증된 거리가 아니다. 구간 중간 지점에서 시설까지의 직선거리로 계산한다.

```text
거리 계수 = max(0, 1 - 거리 / 검색 반경)
r = clamp(위험구역 감점 합, 0, 1)
시설별 적용 보너스 = 가중치 × 거리 계수 × (1 - r)
b = min(적용 보너스 합, 0.10)
구간 환경 점수 = clamp(0.50 - r + b, 0, 1)
```

0.50은 미확인 상태의 비교 기준점이며 안전 확률 50%가 아니다. 위험이 클수록 시설 보너스가 줄어든다. 감점이 없고 가로등이 50m 떨어진 경우 두 연령대 모두 보너스는 0.02, 점수는 0.52다. 경찰시설이 30m 떨어진 경우 그 시설의 보너스는 `0.04 × (1 - 30/150) = 0.032`다. 세 종류가 모두 바로 옆에 있어도 최대 점수는 0.60이다. 적용 내역에는 위험에 따른 감쇠까지 반영한 실제 값을 저장한다.

**도로망 Min-Max 정규화는 제거했다.** 같은 위험·시설 입력의 구간은 다른 도로가 추가되어도 점수가 같다. 실제 연결이 달라지면 경로 자체는 달라질 수 있다. A* 비용은 기존 `거리 × [1 + 0.55 × (1 - 점수) × 6]`, 최단 경로는 거리만 사용한다. 화면 점수는 구간 환경 지표의 평균이며 안전 인증이나 범죄 확률을 뜻하지 않는다. 이전 앱이 저장한 Min-Max 점수와 현재 점수를 직접 비교하지 않는다. 기존 위험 감점은 여전히 목업 위험구역이고 실제 범죄·사고 데이터를 연동한 것은 아니다.

## 연구에서 확인한 범위

- [Piza 외, 2019 CCTV 메타분석](https://doi.org/10.1111/1745-9133.12419): 효과는 장소·운영 조건에 따라 달랐다. 주차장·주거지역의 결과를 모든 도로와 연령대에 일반화하지 않는다.
- [Welsh 외, 2022 조명 개선 메타분석](https://doi.org/10.1111/1745-9133.12585): 지역 단위 조명 개선의 결과이며 가로등 한 곳이나 100m 범위의 계수로 옮기지 않는다.
- [Oxfordshire 통학로 평가 지침](https://www.oxfordshire.gov.uk/schools/travelling-school/safe-walking-routes): 보도·시야·교통량·속도·횡단 난이도·사고 이력 등을 검토한다. 여기서 한국 서비스의 14세 기준이나 수치 계수를 도출하지 않는다.

공통 기준과 연령 보정 후보를 검증하는 [A/B/C 평가 계획](route-weight-evaluation.md)을 별도로 정리했다.

## 가입·기존 계정

- 새 앱의 가입 화면은 생년월일을 받아 `POST /api/auth/signup`의 `birthDate`(YYYY-MM-DD)에 보낸다. 회원 유형은 기존 만 19세 기준으로 정하고 미성년 가입에는 보호자를 입력받는다.
- 이전 클라이언트의 가입 요청은 `birthDate`를 생략할 수 있다. 기존 계정과 동일하게 새 앱에서 경로 계산 전에 입력하도록 한다.
- `GET /api/users/me`는 본인의 `birthDate`를 포함한다.
- `PATCH /api/users/me/birth-date`에 `{"birthDate":"2014-11-13"}`을 보내 등록·수정한다. 1900-01-01 이전, 미래, 누락 날짜는 거절한다. 회원 유형을 이 요청으로 바꾸지는 않는다.
- 기존 계정이 새 앱에서 경로를 계산할 때 생년월일이 없으면 날짜 선택 창을 표시하고 저장 후 다시 계산한다. 내 정보 화면에서도 수정할 수 있다.
- 생년월일은 사용자가 입력한 정보다. 법정대리인 확인·동의 기능을 의미하지 않는다. 기존 보호자 등록/연결 기능도 그 동의 절차를 대신하지 않는다.

## 경로 계산·기록

인증이 필요한 `GET /api/routes/safety-profile`은 본인의 연령대와 DB 가중치를 반환한다.

```json
{
  "ageBand": "UNDER_14",
  "birthDateRequired": false,
  "facilityWeights": {
    "CCTV": 0.02,
    "STREET_LIGHT": 0.04,
    "POLICE": 0.04,
    "EMERGENCY_BELL": 0.0,
    "CONVENIENCE_STORE": 0.0,
    "FIRE_STATION": 0.0
  }
}
```

위 예시는 `ApiResponse.data` 내부다. 생년월일이 없으면 `ageBand:null`, `birthDateRequired:true`, `facilityWeights:{}`를 반환한다. 가중치가 누락되거나 잘못 설정되면 다른 연령대의 값으로 대체하지 않고 오류로 처리한다.

앱은 경로를 계산할 때마다 이 API를 조회한다. 연령대나 가중치가 바뀌면 캐시한 그래프도 다시 계산하므로 생일 경과와 DB 조정이 반영된다. 조회 실패 시 로그인 사용자의 연령대를 임의로 바꾸지 않는다.

안내 시작 요청 `POST /api/routes`에 계산 당시 `safetyAgeBand`를 보낸다. 서버는 현재 연령대와 일치하는지 먼저 확인한 후 `route.safety_age_band`에 기록한다. 생일 경과 등으로 달라졌다면 재계산을 요구하고 진행 중인 경로를 취소하지 않는다. 계산된 시설별 `appliedScore`는 기존처럼 `segment_facility`에 저장한다. 이전 앱은 새 필드를 생략할 수 있고 그 경로의 스냅샷은 NULL로 남긴다.

## DB 가중치 조정 예시

```sql
UPDATE route_facility_weight SET weight = 0.05
WHERE age_band = 'UNDER_14' AND facility_type = 'STREET_LIGHT';
```

새 DB는 `01_full_schema.sql` → `03_seed_base.sql` → (선택) `04_enable_rls.sql`, 기존 DB는 `09_route_age_weights.sql` → `10_common_route_weights.sql` → **`11_police_route_weights.sql`**을 적용하고 백엔드와 앱을 함께 배포한다. 이미 10까지 적용한 DB에는 11을 실행한다.

10과 11은 각각 최초 실행 시 기존 가중치를 `route_weight_policy_history`에 백업하고 해당 정책으로 전환한다. 재실행 시 전환 이후 조정한 값을 덮어쓰지 않는다. 과거 경로를 재계산하지 않는다. 튜닝할 때는 두 연령대의 예산을 맞추고 합계를 0.10 이하로 유지한다. 운영 DB 적용은 별도로 수행해야 한다.

스키마 적용 후 `tests/route_age_weights.sql`로 기본 제약을, 초기값 상태의 테스트 DB에서 `tests/common_route_weights.sql`로 공통 가중치와 합계를 검증할 수 있다. 테스트 데이터는 ROLLBACK된다.
